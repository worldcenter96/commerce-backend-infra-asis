# ADR-012. 인스턴스·AZ 배치와 서브넷 구성: 한 AZ에 모으기, 용도별 서브넷

| 항목 | 값 |

| 날짜 | 2026-11-12 |

| 근거 문서 | [design-review-summary.md DR-15](../reviews/design-review-summary.md), [04-design/network.md](../04-design/network.md) 2절, 결정자 구성도(2026-11-12) |

## 맥락

- ADR-007은 인스턴스를 AZ-A 한 곳에 모으고, 서브넷은 AZ마다 퍼블릭·프라이빗을 하나씩 두기로 했다.
- 그 뒤 결정자가 준 구성도에 따라 04-design/network.md가 서브넷을 용도별로 나눴다(퍼블릭 3개, 프라이빗 7개).
- 설계 리뷰 DR-15(COST-04)는 ADR-007과 network.md가 서로 다르다고 지적했고, 결정자는 "network.md에 맞춰 내용을 수정"으로 정했다.
- 그 사이 결정된 사항도 이 ADR에 함께 담는다. NLB는 AZ-A 하나에만 둔다(ADR-010, network.md N-03). ALB는 프라이빗 서브넷의 내부용이다(ADR-010). 로그 서버는 별도 서브넷에 둔다(network.md N-05). 캐시 서브넷 그룹은 서브넷 하나다(N-06).

## 결정

**인스턴스와 데이터 계층은 AZ-A 한 곳에 모으고(ADR-007과 같음), 서브넷은 용도별로 나눈다.**

| 서브넷 | 종류 | AZ | 용도 |
|---|---|---|---|
| public-a | 퍼블릭 | AZ-A | Bastion, NAT Gateway |
| public-nlb-a | 퍼블릭 | AZ-A | NLB |
| public-b | 퍼블릭 | AZ-B | 예비(리소스 없음) |
| private-alb-a | 프라이빗 | AZ-A | ALB 노드 |
| private-alb-b | 프라이빗 | AZ-B | ALB 노드 |
| private-app-a | 프라이빗 | AZ-A | 앱 서버 3대 |
| private-log-a | 프라이빗 | AZ-A | 로그 서버 |
| private-db-a | 프라이빗 | AZ-A | RDS MySQL |
| private-db-b | 프라이빗 | AZ-B | RDS 서브넷 그룹용(인스턴스 없음) |
| private-cache-a | 프라이빗 | AZ-A | ElastiCache Redis(서브넷 그룹도 이 서브넷 하나) |

- CIDR은 04-design/network.md 2절을 따른다. 이 ADR에는 쓰지 않는다.
- AZ-B에는 인스턴스를 두지 않는다. AZ-B 서브넷은 AZ 2개를 요구하는 리소스(ALB, RDS 서브넷 그룹)와 예비용이다.

## 검토한 대안

| 대안 | 내용 | 결과 |
|---|---|---|
| A. ADR-007대로 | AZ마다 퍼블릭·프라이빗 하나씩, 모두 4개 | 기각 |
| B. 용도별 서브넷 | 위 표의 10개 | **채택**(결정자 구성도, DR-15) |

> 02에서 비교한 대안이 아니다. 결정자 구성도와 리뷰 결정으로 정했다.

## 결과

**장점**
- 서브넷 이름만 보고 어떤 리소스가 있는지 알 수 있다.
- 계층별 예비 대역을 둬서 나중에 서브넷을 늘리기 쉽다(network.md 2절).
- NFR-02, NFR-03, NFR-05를 충족한다. 인스턴스 배치는 ADR-007과 같다.

**단점**
- 서브넷·라우팅 연결·검증 대상이 4개에서 10개로 늘어 2일 구축의 작업량이 늘어난다(설계 리뷰 COST-04, COST-13).
- 접근 통제는 보안 그룹 참조로만 하므로(security.md P-05) 서브넷을 나눠도 접근 통제 효과는 더해지지 않는다(COST-04).
- AZ-A 장애 때 모든 서비스가 멈추는 것은 ADR-007과 같다(00 3.2).

## 관련 요구사항

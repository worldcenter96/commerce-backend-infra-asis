# ADR-009. 비밀값 전달: 애플리케이션 서버 내부의 Secret 파일

## 맥락

- 서비스가 MySQL·Redis에 연결하려면 DB 비밀번호 같은 비밀값을 서버에 전달해야 한다(FR-04). 00과 01에는 전달 방식이 정해져 있지 않았다.
- Local State는 운영자 개인 PC에 둔다(Q-31, CON-11). 액세스 키는 코드에 주석으로 위치를 표기하고 Terraform 실행 전에 넣는다(FR-11).
- 02에서 Terraform 변수 → 사용자 데이터·환경 변수, SSM Parameter Store를 비교했다.

## 결정

**MySQL 비밀값 등은 애플리케이션 서버 내부에 Secret 파일로 둔다.**

- 이유: (기재하지 않음)
- 이 방식은 02 D-09에서 비교한 두 대안(A, B)과 다른 새 방식이다.
- 비밀값은 Terraform 구축 단계에서 넣지 않는다. 넣는 방법은 추후 확정한다. 결정자 지정(2026-11-12)
- 예외: RDS(ADR-008)는 만들 때 마스터 비밀번호가 반드시 필요하다. 그래서 **임시 비밀번호로 만들고, 구축이 끝난 뒤 운영자가 직접 바꾼다.** 결정자 지정(2026-11-12)
- 예외 확대(2026-11-12 결정자 지정, 04-design/security.md S-11): ElastiCache Redis 인증 토큰도 만들 때 지정해야 한다. RDS와 같게 **임시 토큰으로 만들고, 구축이 끝난 뒤 운영자가 직접 바꾼다.** 바꾼 값은 Secret 파일에 둔다.

## 결과

> 채택한 방식은 02 비교표에 없다. 아래 장단점은 02 D-09의 비교 기준(비밀값이 남는 곳, 비용, 난이도)을 적용해 적었다.

**장점**
- 별도 AWS 서비스가 필요 없어 비용이 $0이다.
- 애플리케이션이 파일 하나만 읽으면 되므로 구현이 단순하다.

**단점**
- 비밀값이 서버 디스크(EBS)에 평문으로 남는다. 파일 권한을 제한해야 한다.
- ~~파일을 Terraform 사용자 데이터로 만들면, 02 대안 A처럼 비밀값이 State와 인스턴스 메타데이터에도 남는다.~~ Terraform 구축 단계에서는 비밀값을 넣지 않으므로, Terraform을 거쳐 State나 사용자 데이터에 남지는 않는다(2026-11-12).
- RDS 임시 비밀번호와 Redis 임시 인증 토큰은 State(운영자 PC, Q-31)에 평문으로 남는다. 운영자가 바꾸기 전까지는 이 값으로 DB와 Redis에 접속할 수 있다.
- 비밀번호를 Terraform 밖에서 바꾸면 코드와 실제 값이 달라진다. 다음 `terraform plan`에서 변경으로 잡혀 FR-11 검증(종료 코드 `0`)이 실패하고, `apply`하면 임시 비밀번호로 되돌아간다. 코드에서 이 속성을 변경 감지에서 빼야 한다(예: `lifecycle { ignore_changes = [password] }`, 05에서 확정).
- 서버가 3대이므로 같은 파일을 3곳에 맞춰 둬야 한다(CON-14). 값을 바꾸면 3곳을 모두 고쳐야 한다.

## 후속 조치

- 아래 두 가지를 정하지 않았다. 05 구현 계획 전에 정해야 한다.
  1. Secret 파일을 서버에 넣는 방법(~~Terraform 사용자 데이터,~~ CodeDeploy 배포 묶음, Bastion을 거쳐 직접 복사 등). Terraform 구축 단계는 후보에서 뺐다(2026-11-12). 방법은 추후 확정한다.
  2. 파일 위치와 권한
- 방법에 따라 비밀값이 State, 배포 아티팩트(S3), Git 저장소 중 어디에 남는지가 달라진다. 특히 Git 저장소에 들어가지 않도록 해야 한다.
- RDS 임시 비밀번호와 Redis 임시 인증 토큰(2026-11-12 결정)에 대해 05 구현 계획 전에 정할 것:
  1. 임시 값을 Terraform에 넘기는 방법. 코드에 직접 쓰지 않고 변수로 넘겨야 Git 저장소에 남지 않는다
  2. 값을 바꾸는 시점과 절차(예: 구축 직후 Bastion에서 RDS는 `ALTER USER` 실행. Redis는 인증 토큰 교체 기능으로 바꾸는 방법이 있는 것으로 알고 있다, 확인 필요)
  3. 바꾼 뒤 FR-11 검증이 실패하지 않도록 변경 감지에서 빼는 방법(두 리소스 모두)
- ~~ElastiCache(ADR-008)에 인증 토큰을 쓸지는 아직 정하지 않았다. 쓴다면 같은 방식을 적용할지 정해야 한다.~~ ~~ElastiCache 인증 토큰은 쓰지 않는다. 앱 서버 → Redis 구간에 전송 중 암호화를 쓰지 않기로 해 인증 토큰을 쓸 수 없다(2026-11-12 결정자 지정, 설계 리뷰 DR-07).~~ (2026-11-12 변경, 설계 리뷰 K-03) 앱 서버 → Redis 구간에 전송 중 암호화를 켜기로 해 인증 토큰을 쓸 수 있게 됐다. ~~쓸지는 04-design/security.md S-10에서 정한다. 쓴다면~~ 인증 토큰을 쓰기로 했다(2026-11-12 결정자 지정, security.md S-10). 값은 이 ADR의 Secret 파일 방식으로 둔다. 인증 토큰은 ElastiCache를 만들 때 지정해야 해서, "Terraform 구축 단계에서 비밀값을 넣지 않는다"는 이 ADR의 결정과 부딪친다. 넘기는 방법은 security.md S-11에서 정한다.
- Secret 파일을 서버에 넣는 방법은 Terraform 범위 밖에서 정한다(2026-11-12 결정자 지정, 설계 리뷰 DR-11).

## 맥락

- GitHub Actions가 JAR를 빌드해 S3에 올리고, 서비스별로 서버에 배포한다(CON-09, FR-08).
- 서비스 하나를 배포해도 다른 서비스는 바뀌지 않아야 하고(NFR-10), 배포가 끝나면 `/healthz`가 200이어야 한다(NFR-11). 롤백은 이전 버전을 수동으로 다시 배포한다(NFR-08).
- 사용자 선호는 CodeDeploy였고(Q-23), 02에서 CodeDeploy, SSM Run Command, SSH 스크립트를 비교했다.

## 결정

**AWS CodeDeploy를 채택한다.** (02 D-02 대안 A)

- 이유: 배포 이력과 상태 추적이 간편함

## 결과

**장점** (02 D-02 비교표)
- 서비스마다 배포 그룹을 분리하므로 NFR-10을 충족한다.
- 이전 리비전을 다시 배포해 NFR-08을 충족한다.
- `ValidateService` 훅에서 배포 뒤 응답을 확인해 NFR-11을 충족한다.
- 공용 IAM 사용자 키 하나로 동작한다(NFR-07). EC2 대상이라 비용은 $0이다.

**단점** (02 D-02 비교표)
- 프라이빗 서버에서 CodeDeploy 엔드포인트까지 아웃바운드가 필요하다(FR-05, ADR-004).
- 에이전트에 Ruby가 필요하다. Ubuntu 24.04 공식 지원 여부를 확인해야 한다(A-06, 확인 필요).
- 에이전트가 서버마다 메모리를 약 50~100MB 쓴다(CON-14).
- 운영 부담은 중간이다. appspec, 배포 그룹, 서비스 역할, 에이전트를 관리해야 한다. 구현 난이도는 중이다.

**후속 조치**
- 구축 첫날 Ubuntu 24.04에 CodeDeploy 에이전트가 설치·동작하는지부터 확인한다(A-06).

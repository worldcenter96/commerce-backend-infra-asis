## 맥락

- 03 리뷰 A-01은 인터넷 게이트웨이(IGW), 라우팅 테이블, 보안 그룹이 03 어디에도 없다고 지적했다. IGW가 없으면 NLB, NAT Gateway, Bastion이 인터넷과 통신할 수 없다.
- 보안 그룹은 ADR-003(ALB는 NLB에서 오는 트래픽만 받음)과 ADR-005(Bastion SSH 출발지 제한)가 이미 전제로 깔고 있었다.
- 앱 서버는 프라이빗 서브넷에 있고 NAT Gateway로 나간다(FR-05, ADR-004). FR-04와 NFR-14는 Bastion에서 MySQL·Redis에 접속해 검증한다.
- 02에서 대안을 비교하지 않았다. 결정자가 리뷰 답변으로 바로 정했다.

## 결정

### 인터넷 게이트웨이와 라우팅 테이블

- VPC에 **인터넷 게이트웨이 1개**를 둔다.
- **퍼블릭 서브넷**(NLB, NAT Gateway, Bastion)은 IGW로 직접 나간다.
- **프라이빗 서브넷**(앱 서버, 로그 서버, ALB, RDS, ElastiCache)은 NAT Gateway를 거쳐 IGW로 나간다. 결정자 확인(2026-11-12)
- 그래서 라우팅 테이블은 퍼블릭용(기본 경로 → IGW)과 프라이빗용(기본 경로 → NAT Gateway) 두 종류다. NAT Gateway가 AZ-A에 하나뿐이므로(ADR-004, ADR-012 → ADR-014) AZ-B 프라이빗 서브넷도 AZ-A의 NAT Gateway를 쓴다.

### 보안 그룹

| 대상 | 들어오는 트래픽 허용 | 근거 |
|---|---|---|
| ALB | NLB에서 오는 HTTPS만 | ADR-003 |
| 앱 서버 EC2 (admin / b2b / b2c) | **ALB 보안 그룹에서 오는 앱 포트만.** 출발지는 0.0.0.0/0이 아니라 ALB 보안 그룹으로 지정한다 | 결정자 확인(2026-11-12) |
| MySQL(RDS), Redis(ElastiCache) | **앱 서버 3대와 Bastion에서 오는 MySQL 포트, Redis 포트만** | 결정자 확인(2026-11-12) |

- 결정자의 첫 답변은 "ALB와 EC2 서버 사이 0.0.0.0/0, 443 허용"이었다. ALB가 TLS를 복호화하므로 ALB → 앱 서버 구간은 앱 포트(HTTP)를 쓰고, 출발지는 ALB 보안 그룹으로 좁히기로 바꿨다(2026-11-12).
- 포트 번호, CIDR, 출발지를 IP로 지정할지 보안 그룹으로 지정할지 같은 **상세 값은 04-design에서 정한다.** 03 규칙에 따라 03에는 쓰지 않는다.

## 검토한 대안

비교하지 않았다. 결정자가 리뷰 답변으로 바로 정했다.

> CLAUDE.md는 설계 결정마다 대안을 2개 이상 비교하도록 한다. IGW와 라우팅 테이블은 퍼블릭·프라이빗 서브넷 구조(ADR-012 → ADR-014)와 NAT Gateway(ADR-004)를 고르면 따라오는 구성이라 대안이 사실상 없다. 보안 그룹 규칙은 결정자 지시로 비교를 건너뛰었다.

## 결과

**장점**
- NLB, NAT Gateway, Bastion이 인터넷과 통신할 수 있다(FR-05, FR-06, FR-07).
- 앱 서버는 ALB에서만, 데이터 계층은 앱 서버와 Bastion에서만 닿는다(NFR-06).
- Bastion에서 MySQL·Redis에 바로 접속해 FR-04, NFR-14를 검증할 수 있다.
- IGW와 라우팅 테이블, 보안 그룹은 요금이 없다(추정치).

**단점**
- AZ-B 프라이빗 서브넷도 AZ-A의 NAT Gateway를 쓴다. AZ-A에 장애가 나면 아웃바운드가 모두 끊긴다. 고가용성을 보장하지 않으므로 받아들인다(00 3.2).

> **읽는 법**
> - **근거**: 00-context.md에 붙어 있는 출처 ID를 그대로 쓴다. `Q-x-xx`는 discovery 질문, `A-xx`는 00의 가정, `Q-xx`는 00의 미정 사항(해결됨)이다.
> - **요구사항 문장**: "무엇을, 얼마나"만 적는다. 어떤 AWS 서비스로 구현할지는 02-options에서 정한다. 이미 고정된 기술은 5절 제약사항에만 적는다.
> - **우선순위**: 구축 기간 2일(00 5.2)을 기준으로 정했다.
>   - **Must**: 없으면 MVP 검증(배포, 연동, 기본 운영)을 할 수 없다.
>   - **Should**: 2일 안에 하는 것이 목표지만, 밀리면 운영 기간에 해도 된다.
>   - **Could**: 시간이 남으면 한다.
> - **검증 방법의 표기**: `<...>`는 02 이후에 정해질 값이다(예: 서버 주소, 버킷 이름).

## 1. 목적

- 의류 커머스 백엔드 3개 서비스(admin / b2b / b2c)를 위한 AWS 인프라를 서울 리전에 신규 구축한다.
- 개인 MVP로서 배포, 연동, 기본 운영을 최소 비용으로 검증한다.
- 구축 2일, 운영 2일(하루 2시간)이 끝나면 리소스를 모두 삭제한다.

## 3. 기능 요구사항 (FR)

| ID | 요구사항 | 근거 | 우선순위 | 검증 방법 |
|---|---|---|---|---|
| FR-02 | 서비스 도메인 3개에서 유효한 인증서로 HTTPS(443) 요청을 받는다. | Q-S-04, Q-O-07 | Must | 도메인 3개 각각에 HTTPS로 서비스 기능 경로(예: `https://<도메인>/signup`)에 접속해 인증서 오류 없이 기능이 동작하는지 검증한다. |
| FR-03 | 도메인별로 들어온 요청을 해당 서비스로 보낸다. admin 도메인은 admin 서비스, b2b 도메인은 b2b 서비스, b2c 도메인은 b2c 서비스로 간다. | Q-O-07, Q-B-02 | Must | 도메인마다 해당 서비스의 기능 경로(예: `https://<도메인>/signup`)에 접속해 그 서비스의 기능이 동작하는지 검증한다. |
| FR-04 | 세 서비스가 같은 MySQL 8.x 1개와 Redis OSS 7.x 1개에 연결한다. Redis에는 로그인 세션을 저장한다. | Q-B-03, Q-15 | Must | 관리 접속 경로의 서버(사용자 선호: Bastion, 02에서 확정)에서 (1) `mysql -h <MySQL 주소> -u <사용자> -p -e 'SELECT 1'`이 성공한다. (2) `redis-cli -h <Redis 주소> <인증·암호화 옵션> PING`의 결과가 `PONG`이다. |
| FR-05 | 프라이빗 네트워크에 있는 서버가 빌드 아티팩트 저장소와 배포 도구, 일반 인터넷으로 아웃바운드 통신을 할 수 있다. | Q-B-04, Q-34 | Must | 프라이빗 서버에서 `curl -sI https://s3.ap-northeast-2.amazonaws.com`의 응답 코드가 있다. 배포 1회가 성공한다(FR-08). |
| FR-06 | 서비스 진입점은 고정 공인 IP로 요청을 받는다. 협력사가 이 IP를 자기 방화벽의 나가는 쪽 허용 목록에 등록할 수 있어야 한다. 리소스를 중지했다가 다시 시작해도 이 IP는 바뀌지 않는다. 나가는 쪽 아웃바운드는 고정 IP가 필요하지 않다. | Q-B-04, Q-05, Q-36 | Must | 서비스 도메인 3개 각각에 `dig <도메인> +short`를 실행해 결과를 기록한다. 리소스를 중지했다가 다시 시작한 뒤(CON-03) 다시 실행했을 때 같은 값이 나온다. |
| FR-07 | 운영자는 관리 접속 경로 하나를 거쳐서만 서버와 DB에 접근한다. | Q-S-04, Q-O-06 | Must | (1) 관리 접속 경로를 거쳐 서버에 접속하고 `mysql -h <MySQL 주소> -u <사용자> -p -e 'SELECT 1'`이 성공한다. (2) 인터넷에서 직접 접근하는 시도는 실패한다(NFR-06). |
| FR-08 | CI/CD 파이프라인이 JAR를 빌드해 아티팩트 저장소에 올리고, 서비스별로 서버에 배포해 실행한다. 배포는 수동으로 실행하거나 파이프라인으로 트리거한다. | Q-O-02, Q-O-04, Q-B-02 | Must | (1) `gh workflow run <워크플로>` 실행 후 `gh run watch`가 성공으로 끝난다. (2) `aws s3 ls s3://<아티팩트 버킷>/<서비스>/`에 새 JAR가 보인다. (3) 서버의 JAR와 아티팩트의 `sha256sum` 값이 같다. |
| FR-09 | 3개 서비스의 애플리케이션 로그를 한곳에 모아 서비스별로 조회한다. | Q-O-03 | Should | 각 도메인에 요청을 1건 보낸 뒤, 로그 조회 화면에서 서비스 이름으로 검색하면 3개 서비스 모두 결과가 1건 이상 나온다. |
| FR-11 | 인프라 리소스 전체를 코드로 만들고, 바꾸고, 지운다. **IAM 리소스(인스턴스 프로파일, 역할, 사용자 등)는 예외로 Terraform 코드에 넣지 않는다.** 액세스 키가 필요한 부분은 코드에 주석으로 표기하고, Terraform 실행 전에 코드에 넣는다. | Q-O-05, Q-20, 설계 리뷰 K-04 | Must | (1) `terraform apply` 직후 `terraform plan -detailed-exitcode`의 종료 코드가 `0`이다(코드와 실제 상태 사이에 차이 없음). (2) 코드에서 액세스 키가 필요한 위치마다 주석이 있다. |
| FR-13 | admin / b2b / b2c 서비스마다 상태 확인 경로 `/healthz`를 둔다. 서비스가 정상이면 이 경로는 HTTP 200을 준다. 서비스 진입점은 이 경로로 각 서비스의 상태를 확인한다. | Q-30 | Must | (1) 도메인 3개 각각에 `curl -s -o /dev/null -w '%{http_code}' https://<도메인>/healthz`를 실행하면 `200`이 나온다. (2) 진입점의 대상 상태 조회(`<조회 명령>`, 02 이후 확정)에서 3개 서비스가 모두 정상이다. (3) 서비스 하나의 프로세스를 멈추면 같은 조회에서 그 서비스만 비정상이 된다. |

## 4. 비기능 요구사항 (NFR)

> 00에서 "정의하지 않음"으로 확정한 항목(SLA/SLO, RTO/RPO, 백업, 메트릭·알람, 시작 소요 시간, 로그 보존 기간)에는 새 목표 수치를 만들지 않았다. 대신 00의 확정 사항에서 측정할 수 있는 목표만 끌어냈다. 정의하지 않은 항목은 6절 추적표에 이유를 적었다.

## 1. 배경과 목적

- 의류 커머스 백엔드(admin / b2b / b2c)를 운영할 AWS 인프라를 **신규 구축**한다. 기존 시스템을 이전하지 않는다. (Q-B-01)
- **개인 MVP 프로젝트**다. 용량은 기능과 인프라 동작을 검증하는 데 필요한 최소 리소스를 기준으로 잡는다. (Q-T-01)
- MVP 단계에서는 **서비스 배포, 연동, 기본 운영**을 우선 검증한다. 대규모 트래픽 확장과 운영 고도화는 초기 범위에서 제외한다. (Q-B-06)
- 구축 대상은 **백엔드 인프라**뿐이다. 프론트엔드 웹/앱과 정적 웹 호스팅은 범위에서 제외한다. (Q-B-05)

## 2. 사용자와 이해관계자

### 2.1 서비스 채널

| 채널 | 사용자 | 실행 형태 | 접근 방식 | 트래픽 성격 | 출처 |
|---|---|---|---|---|---|
| admin | 사이트 관리자 | 독립 실행 애플리케이션(배포 단위 1개) | 인터넷에서 HTTPS(443)로 접근. 외부 공개 허용 | 정량 목표 없음. 기능 검증 수준 | Q-B-02, Q-B-03, Q-S-04, Q-T-01, Q-22 |
| b2b | 의류 판매자 | 독립 실행 애플리케이션(배포 단위 1개) | 인터넷에서 HTTPS(443)로 접근 | 정량 목표 없음. 대량 주문·정기 배치와 거래처 API 연동은 범위 제외 | Q-B-02, Q-S-04, Q-T-01, Q-T-07, Q-S-05, Q-22 |

- 세 채널 모두 국내 사용자만 대상으로 한다. (Q-T-06)

- 채널별 기능 차이는 논의에서 제외한다. (Q-22)

## 3. 확정 사항

### 3.1 애플리케이션

| 항목 | 내용 | 출처 |
|---|---|---|
| 구조 | 멀티모듈. 배포 단위 3개가 admin / b2b / b2c와 1:1로 대응 | Q-B-02 |
| 실행 | admin / b2b / b2c를 독립적으로 실행. 서비스별로 서버를 따로 두고, 서비스별 인스턴스는 1개씩(Auto Scaling 없음) | Q-B-03, Q-17 |
| 데이터 규모 | MVP만 구현할 예정이기에 최소한의 스펙 | Q-T-04, Q-14 |
| 데이터 계층 | 세 서비스가 MySQL 8.x와 Redis OSS 7.x를 함께 사용 | Q-B-03 |
| Redis 용도 | 사용자 로그인 세션 저장. 세션이 유실돼 사용자가 다시 로그인해야 하는 상황을 허용 | Q-15 |
| 장애 격리 | 애플리케이션 실행 계층에서만 격리. 공유 MySQL·Redis의 단일 장애점 위험은 수용 | Q-B-03, Q-A-05 |
| 외부 연동 | 프라이빗 네트워크에서 S3와 CodeDeploy에 접근해야 함. 일반 인터넷 아웃바운드도 필요. 거래처 API 등 그 밖의 외부 연동은 제외 | Q-B-04, Q-34 |
| 고정 공인 IP | 현재 필요. 인바운드 시 필요. 협력사가 자기 방화벽의 나가는 쪽 허용 목록에 이 IP를 등록한다. 나가는 쪽(NAT)은 고정 IP가 필요하지 않다 | Q-B-04, Q-05, Q-34, Q-36 |
| 외부 네트워크 경로 | NAT 경유. NAT Gateway로 구성(만들 때 EIP가 하나 붙지만 고정 IP 요구 때문은 아님) `[비교 대상]` | Q-B-04, Q-23, Q-36 |
| 진입점 고정 공인 IP | 서비스 진입점 앞단에 NLB를 두고 EIP를 붙인다. 사용자 요청은 NLB → ALB 순서로 들어온다 | Q-36 |
